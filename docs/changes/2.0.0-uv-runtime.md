# 2.0.0 — uv environments, one launcher, containers as fallback

Design notes and change log for the release that replaces the ~20 conda
environments with uv projects: three shared ones and one per research stack. Upgrade steps are in
[2.0.0-migration.md](2.0.0-migration.md); what was tested where is in
[2.0.0-verification.md](2.0.0-verification.md).

## Goal

A user installs AtomisticSkills with almost no effort -- as a Claude Code plugin
or a clone -- on x86_64 or aarch64, and every skill, skill script and MCP tool
works afterwards.

## Design

- **Three uv projects** under `venv/`: `cpu` (no torch), `mlip` (MACE, MatGL),
  `fairchem` (FairChem). Optional extras keep packages with system requirements
  out of the base sets: `openmm` (glibc 2.34 wheels), `pymol` (x86_64 only),
  `docking` (Vina; Boost on aarch64), `void` (git source), `transport` (AMSET;
  BoltzTraP2 needs git + cmake at build time).
- **Research stacks** that cannot share those environments (an old torch, or a
  compiled extension built for one torch version) get their own small uv
  project each, pinned to what they were verified with: `adit`, `diffcsp`,
  `mattergen`, `msms`, `reactot`, `scd` (see Research stacks below).
- **One launcher, `venv/run`**, for skill commands (`venv/run <env>[+extra] cmd`)
  and MCP servers (`venv/run --server <name>`). Backend: uv on the host when it
  can (Linux, glibc floor from `venv/platforms.tsv`, compiler for a first build),
  else a container image built from the same lock, with host paths mounted at the
  same locations. `--setup` and `--doctor` for installation and diagnosis.
- **Skills are self-locating**: commands use `${CLAUDE_SKILL_DIR}/../../venv/run`,
  which Claude Code substitutes for project, personal and plugin skills alike.
  `metadata.venv` records the environments a skill uses.
- **MCP tools keep working without a connected server**: `python -m
  src.mcp_server.cli <server> <tool> key=value ...` calls the same FastMCP tool,
  several tools per process so `load_model` state persists.
- **Workspace**: results go to the user's project (`ATOMISTIC_WORKSPACE`, else the
  repository for a checkout, else the current directory), never to the plugin
  cache. MCP servers get `${CLAUDE_PROJECT_DIR}` from plugin.json.
- **Images**: all built from the uv locks: `cpu`, `mlip`, `fairchem` (amd64 +
  arm64), and `generative` (amd64 + arm64), which installs `adit`, `diffcsp`
  and `mattergen` side by side (on arm64 compiling their PyG extensions with
  CUDA).
- **No conda**: the research stacks have their own uv projects, and LAMMPS
  builds against `venv/mlip` (`mlip+lammps`); `conda-envs/` is gone.

## Versions

Everything tracks its latest release. Floors (not pins) keep the science packages
current, because an unbounded resolve preferred newest torch/numpy and fell back
to fairchem-core 1.0.0 and nvalchemi 0.1.0.

| :--- | :--- | :--- | :--- |
| torch | 2.14.1, +cu130 or +cu126 | 2.13.0, +cu130 or +cu126 | — |
| mace-torch / e3nn | 0.3.16 / 0.4.4 | — | — |
| matgl | 4.1.0 (PyTorch Geometric only) | — | — |
| fairchem-core / e3nn | — | 2.23.0 / 0.6.0 | — |
| nvalchemi-toolkit | 0.2.0 | 0.2.0 | — |
| numpy | 2.3.5 | 2.3.5 | 2.5.3 |
| pandas | 3.0.6 | 3.0.6 | 3.0.6 |

**Conflicts that force separate environments**

1. `mace-torch` pins `e3nn==0.4.4`; `fairchem-core` needs `e3nn>=0.5` → `mlip` and
   `fairchem` cannot merge.
2. `fairchem-core` 2.23 requires `torch~=2.13`; `mlip` takes torch 2.14.1.
3. `nvalchemi-toolkit` 0.2 requires `numpy<2.4`, so the GPU projects get numpy
   2.3.5 while `cpu` gets 2.5.3.

## Research stacks

| Project | Pinned to | Python | Torch | Platforms |
| :--- | :--- | :--- | :--- | :--- |
| `adit` | closed set of the verified 1.x environment | 3.10 | 2.9.1, cu126 / cu130, PyG wheels | x86_64 with glibc >= 2.32; elsewhere the `generative` image |
| `diffcsp` | closed set of the verified 1.x environment | 3.11 | 2.10.0, cu126 / cu130, PyG wheels | x86_64 with glibc >= 2.32; elsewhere the `generative` image |
| `mattergen` | closed set of the verified 1.x environment | 3.10 | 2.9.1, cu126 / cu130, PyG wheels | x86_64 with glibc >= 2.32; elsewhere the `generative` image |
| `reactot` | closed set of the verified 1.x environment | 3.10 | 2.2.1 (cu121 on x86_64, CPU on aarch64) | x86_64, aarch64 |
| `msms` | ms-pred at commit `708148c` (ICEBERG 2.1) | 3.12 | 2.6.0, CPU, DGL 2.5 | x86_64 with glibc >= 2.31 and GCC 9's libstdc++ |
| `scd` | SelfConditionedDenoisingAtoms' `requirements.txt` | 3.12 | 2.10.0, cu126 / cu130, PyG wheels | x86_64 with glibc >= 2.32 |

- The closed sets reproduce the `pip install --no-deps` environments the stacks
  were verified in: every package is pinned and also an override, so upstream
  pins that cannot hold on current GPUs do not move them; packages whose own
  requirements pin an old torch (`mattergen`, `mattersim`) get none
  (`[[tool.uv.dependency-metadata]]`, the equivalent of `--no-deps`).
- PyG's compiled extensions (`torch-scatter`, `torch-sparse`, `torch-cluster`)
  and DGL publish x86_64 wheels only. The generative projects are locked for
  aarch64 too, with the extensions as source builds (static metadata, torch
  matched to the environment); `tool.atomisticskills.native-arches` keeps
  aarch64 hosts on the `generative` image, which does that build with
  `FORCE_CUDA=1` (`docker/Dockerfile.cuda`). `msms` and `scd` are x86_64 only.
- Those wheels understate what they need: the PyG builds for torch 2.9/2.10 are
  tagged `linux_x86_64` but call glibc 2.32, and DGL 2.5 is tagged `manylinux1`
  but needs GLIBCXX_3.4.26 (GCC 9). `tools/scan_wheel_floors.py` measures the
  symbols a wheel uses, `tools/lock_platforms.py` applies the measured floors
  to `venv/platforms.tsv`, and an unmeasured generic-tag wheel fails the table.
  So a RHEL 8 host (glibc 2.28) is sent to the `generative` image rather than
  failing at import, and `msms` needs a GCC 9+ `libstdc++` on the library path.
- Upstream repositories that are not packages are cloned at pinned commits:
  React-OT by `setup_react_ot.py`, SCD by the skill's First Checks, both into
  `~/.cache/atomisticskills`; the ADiT, DiffCSP++ and MatterGen checkouts stay
  next to the project (or `$ADIT_REPO`, `$DIFFCSP_REPO`, `$MATTERGEN_REPO`),
  and `venv/run` mounts them into the container. MatterGen is installed from
  PyPI for its dependencies but imported from its checkout: its distributions
  omit the data files it needs.

**Pins that remain, with reasons**

- `mcp<2` — all ten servers use the 1.x `FastMCP` API; mcp 2 renamed it to
  `MCPServer` and changed the run loop. Porting is a follow-up.
- `pymol-open-source==3.2.0a0` — the only release with Python 3.12 wheels.

**Consequences to know**

- Two torch builds per GPU project, locked as mutually exclusive extras and
  chosen by `venv/run` from the NVIDIA driver: `cu130` (CUDA 13, driver >= 580,
  required for GB10's sm_121 and Blackwell) and `cu126` (CUDA 12.6, drivers
  >= 525; torch >= 2.12 publishes no CUDA 12.8 builds). Both lab test machines
  ran driver 550. `ATOMISTIC_TORCH_CUDA` overrides; images carry cu130. Warp
  1.17 (NValchemi) is built with CUDA 12.9 and runs under either.
- kaleido >= 1 (required by plotly 7) needs Chrome/Chromium for static image
  export; `plotly_get_chrome` installs one on x86_64, aarch64 needs a distribution
  Chromium.
- CHGNet now means the matgl 4.1 checkpoint `CHGNet-PES-MatPES-PBE-1M-2026.9`
  (aliases `CHGNet`, `CHGNet-MatPES-PBE`; `CHGNet-MatPES-r2SCAN` →
  `CHGNet-PES-MatPES-r2SCAN-1M-2026.9`). Versioned 2025 names still load the
  weights they name. Energies differ from the 2025 checkpoint (Si, 2 atoms:
  −10.848 vs −10.761 eV), so results are not comparable across the change.

## Bugs found and fixed along the way

- Locks were uninstallable on every platform (kaleido 0.2.1.post1 has no
  x86_64/aarch64 wheel); now caught at lock time by `required-environments`.
- ~100 scripts imported `src` without it being on `sys.path` (fixed by installing
  the repository into each project as an editable package).
- Dependencies missing from the uv projects: mpcontribs-client, rxn4chemistry,
  feedparser, pymatgen-analysis-defects, optimade http-client, python-pptx,
  nvalchemi-toolkit.
- `chem-msms-predict` was written against the ICEBERG 2.0 API while the 1.x
  install script cloned ms-pred `main` (2.1), so it could not run as shipped;
  the local 1.x environment also failed to import DGL. Ported to 2.1 (atom-mask
  fragments to SMILES, `num_cpu_workers`), with a loud failure when the
  prediction subprocess fails (ms-pred only skips writing a marker), a weights
  download script, and `TORCH_FORCE_NO_WEIGHTS_ONLY_LOAD` for the authors'
  checkpoints under torch 2.6.
- `ml-property-predict-scd` claimed the `mlip` environment, but the upstream
  code imports PyG's compiled extensions; its templates also loaded checkpoints
  whose model config path is relative to the SCD checkout. Now `venv/scd`, and
  the templates load the model from the checkout.
- The ADiT wrapper found its repository through `PYTHONPATH`, which only the
  1.x conda MCP configuration set; under `venv/run` it fell back to paths
  relative to the working directory. The `generative` image carries neither the
  ADiT nor the DiffCSP++ repository, and only the project, workspace and cwd
  were mounted. Now `$ADIT_REPO` (else a sibling `adit`), and `venv/run` mounts
  both checkouts.
- MatGL: DGL is gone in matgl >= 4. Ported the property-predictor trainer to PyG,
  removed DGL code paths, fixed a missing `import torch` in the fine-tuning script
  and a lattice/state mix-up in the PES feature calculator.
- MD observer subclassed matgl's, which assumes a MatGL calculator: MACE MD failed
  under matgl 4.1. Now a backend-agnostic observer.
- `mat-elasticity --help` crashed (unescaped `%`); `np.trapz` removed in numpy 2.4.
- The three DFT `generate_inputs.py` scripts submitted to a hard-coded personal
  jobflow-remote project instead of writing the flow they promise; now they write
  JSON and submit only with `--submit --project --worker`.
- NValchemi batch relax/MD raced a CUDA stream: entering an nvalchemi dynamics
  object switches PyTorch to its own stream, while nvalchemiops' batched cell
  list launches Warp kernels on the default one, so `NeighborListHook` read
  partial neighbor counts ("number of neighbors is larger than the maximum
  allowed: 598 > 112"; it can also silently drop edges). Fixed by binding Warp to
  the dynamics stream (`warp_on_torch_stream`). TensorNet batch MD, disabled for
  this race, is enabled again (NVE drift equal to sequential).
- Batched variable-cell relaxation converged on atomic forces only, so a crystal
  with symmetric forces returned "converged" at step 0 with its cell untouched.
  Convergence now also requires the cell force (virial / N, as ASE's
  `FrechetCellFilter`) to be below `fmax` (`CellForceCriterion`).
- `os.environ["CUDA_LAUNCH_BLOCKING"] = "1"` set inside batch relax had no effect
  (CUDA already initialised) and leaked into every child process; removed.
- ~17 skill scripts crashed at the end of every successful run: an earlier
  refactor left `_params_path.write_text(json.dumps(_config))` lines with
  nothing defining them (NameError after the outputs were written), and
  `define_binding_site.py` called `save_skill_inputs(args, args.output_dir)`
  without an `--output_dir` option, so its stdout mode always failed. Also
  `find_pathways.py` (no `logger`), `benchmark_mlips.py` (no default model
  list), `gcmc_common.py` (helper moved to `src.utils.serialization_utils` but
  call sites not updated), `get_mp_electronic_structure.py` (`CompleteDos`
  not imported) and `smol_utils.py` (scikit-learn names not imported). Found
  with ruff F821; `--help` sweeps cannot see them.
- Every script a SKILL.md names was audited for `--help` safety, import-time
  side effects and outputs written next to the script.
- Stale MCP tool names (`atomate2.submit_vasp_job`, `atomate2.get_task_result`),
  wrong script paths (`skills/qha/...`, `reproduce_table1.py`,
  `calculate_stability.py`), and 35 commands with a bare `python`.

- MatterGen could not generate in the generative image or the x86 uv
  environment: its PyPI distributions omit `sampling_conf` and the GemNet
  scale factors (setuptools without package data). It now runs from a
  checkout. Its fine-tuning example was broken as well (script paths, an import
  typo, the JSON shape, an empty CSV).
- The published 1.x/2.0.0 `generative` image's PyG extensions had no CUDA
  kernels: the image build sees no GPU, so `torch-scatter` and friends compiled
  CPU-only without `FORCE_CUDA=1`. The new build sets it and fails unless each
  extension reports a CUDA version.
- The MCP server tests never ran under uv: the auto-skip keyed on
  `CONDA_DEFAULT_ENV`, and `--strict-markers` knew six of eleven markers. With
  that fixed they found `drugdisc.compute_molecular_fingerprints` failing
  without a heatmap (unbound variable) and six MatGL pretrained models that
  torch >= 2.6 refused to load (numpy arrays and a `Normalizer` in the
  pickles; now allowlisted).
- `+openmm` lacked the OpenFF stack that `drug-complex-system-builder` and
  `drug-mmpbsa-gbsa` import (`openff-toolkit`, `openmmforcefields`,
  `openff-interchange`). Their PyPI releases were yanked (they were not uploaded
  by the maintainers), so they come from the projects' release tags on GitHub.
  So does `python-constraint` 1.4.0, which they require: its only release is a
  bzip2 sdist, which uv >= 0.12 refuses to extract.
  AM1-BCC charges need AmberTools' `sqm`, which no PyPI package carries:
  `--charge_method mmff94|gasteiger` uses RDKit instead, and AM1-BCC or GAFF
  without AmberTools fails with an explanation.
- `sella` (TS search and IRC skills) was missing from `mlip` and `fairchem`, and
  `load_calculator(model_name=None)` crashed those scripts.
- MatGL 4.1 builds property-model graphs on the default CUDA device, so a model
  on the CPU or another GPU failed ("Expected all tensors to be on the same
  device"); the wrapper now builds the graph and moves it to the model's device.
- Containers ignored `CUDA_VISIBLE_DEVICES` (`--gpus all`); `venv/run` now passes
  the selected devices to docker (`--gpus device=...`) and podman (CDI).
- Apptainer cached SIFs by name and tag only, so a SIF pulled from one registry
  or architecture was reused for another; the file name now carries both.
- `venv/run mlip+cu126+lammps` dropped the extras after the CUDA one, and two
  CUDA extras were accepted; both fixed.
- On shared filesystems uv's 300 s lock timeout expired while another node
  synced the same project; `venv/run` waits an hour (`UV_LOCK_TIMEOUT`).
  `tools/mcp_smoke.py` waits at least as long as `ATOMISTIC_SERVER_SETUP_WAIT`.
- `mat-lammps-md`: the MatGL example pip-installed `numpy<2` and `chgnet` into
  the environment (now MatGL's CHGNet); the FairChem example laid CO flat on
  Cu(111) (E_ads +1.3 eV; now carbon-down, -0.39 eV with the oc20 head).

## Known issues and follow-ups

- **NValchemi batch relaxation**:
  - Variable-cell relaxation now uses upstream `FIRE2VariableCell` with
    `tmax=0.5`, `delaystep=5`, and `maxstep=0.2` in both fixed and inflight
    modes. The removed `ScaledFIRE2VariableCell` applied another atom-count
    normalization on top of the normalization already present in ops 0.4.1.
    Standard-form cell preparation is retained. The time-step cap is more
    conservative than the initial `tmax=1.0` candidate, which oscillated on a
    perturbed CHGNet NaCl supercell.
  - Fixed-batch, inflight and sequential ASE results distinguish `success`,
    `not_converged` and `failed`; step exhaustion is not convergence. Inflight
    graduation checks cell stress as well as atomic forces. Each result reports
    its per-structure integration step count.
  - **Upstream blocker:** toolkit 0.2.0 `NeighborListHook` caches periodic image
    ranges and cell-list allocations by total batch dimensions. Replacements
    or cell changes at unchanged dimensions can silently omit neighbors. The
    repair and regression tests belong in NValchemi; no cache workaround is
    embedded here. MatGL wrappers retain `_nvalchemi_supports_inflight=False`
    until a supported dependency release with that repair is validated.
  - **Upstream release limitation:** toolkit 0.2.0 can return energies evaluated
    at moved coordinates after restoring a converged structure's frozen
    coordinates. The first converged trajectory snapshot is preserved when
    extraction is enabled, but the returned live batch (and extraction-disabled
    output) needs the upstream inactive-output repair, already present on
    NValchemi's development branch.
  - Previous variable-cell speedup claims used force-only convergence and have
    been withdrawn from the skill. Publish new timings only after locking and
    validating an upstream release containing both repairs. Tests against an
    edited upstream source checkout are not benchmarks of the committed locks.
- Three example scripts write into their own directory, which in a plugin
  install is the plugin cache: `ml-property-predictor/examples/matgl_bulk_modulus/run_matgl.py`,
  `chem-neb-barrier/examples/butane_conformer/run_example.py`,
  `chem-bond-dissociation/examples/methanol_uma_omol_both/plot.py`.
- Port the MCP servers to mcp 2.x (the 1.x `FastMCP` API is pinned with `mcp<2`).
- AmberTools (`sqm`, `antechamber`, `MMPBSA.py`, `cpptraj`) has no PyPI
  distribution, so no environment carries it: AM1-BCC charges, GAFF and
  `drug-mmpbsa-gbsa`'s AmberTools backend need a separate install, which the
  skills explain. RDKit charges and the OpenMM GBn2 backend need nothing extra.
  OpenFF NAGL charges would remove the `sqm` dependency.
- `msms` and `scd` on aarch64: they need PyG's extensions or DGL built from
  source there (as the `generative` image does).
